実装前の合意用資料です。ジャンルを完全に廃止し、保存した英語表現を主シチュエーションと難易度でAnki deckへ整理するための、DB・UI・API・exportの一貫した設計を示します。

01 / DECISION

この設計で固定すること

CLASSIFICATION ジャンルを廃止する

genre_slug、ジャンル入力、ジャンルfilter、AIのジャンル提案、genre:: Ankiタグをすべて削除する。

PRIMARY SITUATION 主シチュエーションを1つ決める

situation_tags[0]を主シチュエーションとする。2件目・3件目は検索用Ankiタグとして残し、同じカードを複製しない。

STABLE ID IndexはSayDeck固有IDのまま

sentence_variants.anki_indexをAnkiのIndexへ投影する。英語本文の重複に影響されない恒久IDとする。

EXPRESSION LAYERS L1のみ必須、L2〜L4は任意

L1は基本表現として必ず1つ作る。L2〜L4は、情報量・会話性・言い換えに実用上の差がある場合だけ生成し、似た文を水増ししない。

設計上の前提: シチュエーションの命名がdeck名になるため、AI任せの自由な表記揺れは許容しません。AIの提案後、保存前に「主シチュエーション」を既存候補から選び直せるようにします。候補は定義済みプールと最近使ったシチュエーションから出し、未知のものは 未分類 として明示的に扱います。

02 / ANKI PROJECTION

Ankiへ取り込まれるdeckとtags

各variantは、主シチュエーションと表現レイヤーから1つだけのdeckへ投影します。Ankiの1 noteを複数deckに複製しません。

SayDeck └── 友人への返信 ← situation_tags[0]（主シチュエーション） ├── 01_基本表現 (L1 / 必須) ← profile_code ├── 02_詳細表現 (L2 / 任意) ├── 03_会話表現 (L3 / 任意) └── 04_別の自然な言い方 (L4 / 任意) 例: SayDeck::友人への返信::01_基本表現
ノートタイプ

SayDeck ES1Kv2。既存のES1Kv2とは別ノートタイプとして維持する。8フィールドの名称と順序は既存Ankiファイルと揃える。

Anki tags

source::saydecksituation::友人への返信situation::SNS-DMdifficulty::l2

ジャンルタグは出力しない。主シチュエーション以外もtagには残す。

再分類の扱い: 初回export後に主シチュエーションを変更しても、既存Ankiカードを別deckへ自動移動することは保証しません。MVPでは主シチュエーションを「登録時に確定する分類」とし、変更は新しい入力として扱います。再import時のdeck移動を保証したくなった場合は、別要件としてAnki Desktopでの検証と移行仕様を追加します。

B. generation_profiles — 維持

owner_login、code（L1〜L4）、語数・文数制約、instruction。難易度ではなく表現レイヤーの定義として使う。L1のみ必須、L2〜L4は任意。

C. sentence_cards — 維持

D. sentence_variants — 維持

sentence_card_id、profile_code、英文・和訳・基本フレーズ・Anki ID・選択状態。意味単位ごとにL1を必ず1行作り、L2〜L4は学習価値のある差がある場合だけ作る。

E. audio_assets — 維持

variant_idごとにwordとsentenceを1行ずつ。en-USで生成した音声binaryの保存先と検証metadataだけを持つ。

F. anki_exports — 維持

APKG artifactのID、状態、カード数、private storage path、エラーコード。個々のvariantは正本であるsentence_variantsから都度投影する。

owner_login、situation_tag、last_sequence、updated_atを持つ。001を主シチュエーション内の入力連番とする合意が得られた場合だけ追加し、transactionで重複採番を防ぐ。

04 / END-TO-END FLOW

INPUT → LISTS → EXPORT の全体フロー

1INPUT: 日本語を保存

ユーザーは「言いたいこと」を入力する。任意で、最近使った主シチュエーションを選べる。ジャンル操作は存在しない。

INSERT expression_entries
input_ja, situation_tags（任意の先行指定）, status='draft'

2AI: L1と必要な任意表現を生成

AIは意味単位、必須のL1、学習価値がある場合だけL2〜L4、シチュエーション候補を構造化して返す。ユーザーが主シチュエーションを指定済みなら、その分類を優先する。

UPDATE expression_entries.situation_tags
INSERT sentence_cards
INSERT sentence_variants × L1（必須）+ 任意L2〜L4

3REVIEW: 分類と候補を確定

ユーザーは英文候補と「主シチュエーション」を確認する。主タグを配列の先頭にし、L1を必ず選ぶ。主シチュエーション内の入力番号を採番する案もここで実行する。

UPDATE situation_tags, situation_sequence, status='registered', registered_at
UPDATE sentence_variants.is_selected/status

4LISTS: 検索・編集・選択

主シチュエーション、補助タグ、レベル、日付、キーワードで絞り込む。英文・訳・Word等は編集できる。登録済みの主分類は変更しない。

SELECT expression_entries + children
UPDATE sentence_variants
UPDATE is_selected

5EXPORT: 音声・APKGを生成

選択variantごとにWord/Example Sentenceのen-US音声を確認・生成し、主シチュエーションとレベルでdeckを決めてAPKGを作る。

UPSERT audio_assets × 2
INSERT anki_exports
private storageへAPKG保存

6ANKI: import

SayDeck ES1Kv2のnoteとして読み込まれる。IndexとGUIDはDBの恒久値を使うため、同一variantの再importでは重複ではなく更新を目指す。

Deck: SayDeck::主シチュエーション::Lx
Tags: source / situation / difficulty

07 / MANUAL VERIFICATION

動作確認: 同じシチュエーション内で複数prefixを持つ入力

主シチュエーションを約束・予定調整に固定し、短い入力・複数センテンスの入力・会話的な言い換えを順に保存します。これはAIが返す英文そのものを固定するテストではなく、意味単位の分割、連番、任意レイヤー、deck投影を確認するための手動シナリオです。

prefixの設計案: DBには整数のsituation_sequenceを保存し、画面とAnkiのIndexでは3桁ゼロ埋めします。意味単位の番号は既存のsentence_cards.positionから得ます。例: 002-03は「このシチュエーションで2つ目の入力の、3つ目の意味単位」です。999を超えた場合は1000-01と自然に拡張し、文字列切り詰めは行いません。

FIXTURE 001

短い入力 / L1のみ

言いたいこと:
「今日は予定があるので行けない。また別の日にしよう。」

主シチュエーション: 約束・予定調整

期待する意味単位
001-01

必須: L1
不要: L2 / L3 / L4

FIXTURE 002

長い入力 / 3つの意味単位

言いたいこと:
「仕事が長引いていて、待ち合わせに30分ほど遅れそうです。先に始めていてください。着いたらすぐ連絡します。」

主シチュエーション: 約束・予定調整
補助タグ候補: 遅刻・欠席の連絡

期待する意味単位
002-01 / 002-02 / 002-03

各意味単位にL1必須
L2〜L4は差がなければ生成しない

FIXTURE 003

会話的な言い換えを許可

言いたいこと:
「来週末なら時間が取れそうなんだけど、土曜と日曜のどちらが都合いい？」

主シチュエーション: 約束・予定調整

期待する意味単位
003-01

必須: L1
任意: L3（会話として明確に別の言い方がある場合のみ）

確認手順と期待結果

手順画面で確認することDBで確認することAnki exportで確認すること
1. Fixture 001を保存L1は必ず表示される。意味の薄いL2〜L4は表示されない。situation_sequence=1、position=0、L1 variantが1件。SayDeck::約束・予定調整::01_基本表現 に 001-01 が入る。
2. Fixture 002を保存同じ主シチュエーションのまま、3つの意味単位が順番に表示される。situation_sequence=2、position=0/1/2、L1 variantが3件。同じL1 deckに 002-01、002-02、002-03 が追加される。
3. Fixture 003を保存L1を必ず確認。会話上の明確な差がある場合だけL3を候補表示する。situation_sequence=3、L1必須。L3は生成された場合のみ1件。L3が存在する場合だけ 03_会話表現 deckが作られる。L2/L4だけの空deckは作られない。
4. Fixture 002を再export同じ候補を選び直せる。anki_guid と anki_index が初回から不変。Anki Desktopへ再importしても、同じvariantが重複カードにならない。

合意が必要な点: このシナリオは001を「主シチュエーションごとに増える入力番号」として扱います。もし001を「1つの入力内だけの意味単位番号」としたい場合は、既存のsentence_cards.positionだけで足り、situation_sequenceの追加は不要です。

08 / MIGRATION PLAN

ジャンル廃止のDB移行案

このページは実行用SQLではありません。承認後に、番号付きmigrationとして作成・検証します。

予定するmigrationの内容 
BEGIN;

-- 1. 登録済みでタグが空のentryを安全な主分類へ補完
UPDATE expression_entries
SET situation_tags = ARRAY['未分類']::text[]
WHERE status = 'registered'
  AND cardinality(situation_tags) = 0;

-- 2. 登録済みentryのシチュエーションを1〜3件に保証
UPDATE expression_entries
SET situation_tags = situation_tags[1:3]
WHERE cardinality(situation_tags) > 3;

ALTER TABLE expression_entries
  DROP CONSTRAINT IF EXISTS expression_entries_registered_situation_tags_check;

ALTER TABLE expression_entries
  ADD CONSTRAINT expression_entries_registered_situation_tags_check
  CHECK (status <> 'registered' OR cardinality(situation_tags) BETWEEN 1 AND 3);

-- 3. ジャンルを物理削除（新アプリコードの配備後に実行）
ALTER TABLE expression_entries DROP COLUMN genre_slug;

-- 4. シチュエーションfilterを支えるindex
CREATE INDEX IF NOT EXISTS expression_entries_situation_tags_gin
  ON expression_entries USING GIN (situation_tags);

COMMIT;
  • 現在の接続先DBでは、6件中5件にジャンル値があり、削除によりその値は意図どおり破棄される。
  • 登録済み3件のうち1件はシチュエーションが空だった。上記の補完がないと、シチュエーション主軸のdeckへ安全に投影できない。
  • 既存の0007-situation-tag-taxonomy.sqlはこの補完・制約を含むが、現行DBには未適用とみられる。READMEとデプロイ手順のmigration一覧も0006までのため、文書改訂時に是正する。
  • 削除順序は「ジャンルを読まないアプリコードを先に配備 → DB migrationで列をdrop」。旧コードが削除済み列を読む時間帯を作らない。

09 / HUMAN APPROVAL GATE

実装開始前に合意するチェック項目

  • deck名を SayDeck::主シチュエーション::01_基本表現〜04_別の自然な言い方 にする。L1だけ必須で、L2〜L4のdeckは候補がある時だけ作る。
  • ジャンルをUI、API、AI出力、DB、Ankiタグ、LISTS filterから完全に削除する。
  • 主シチュエーションはsituation_tags[0]とし、登録時に確定する。補助タグはdeckを増やさず検索タグとして使う。
  • INPUT / REVIEWに「最近使ったシチュエーションから選ぶ」導線を追加する。ジャンル選択の代わりに、ユーザーが必要な時だけ使える任意操作とする。
  • シチュエーション名の表記揺れを避けるため、AI提案を定義済み候補・最近使った候補へ正規化する。未知の分類は未分類として明示する。
  • 既存のジャンル値は保持せず破棄する。空の登録済みシチュエーションは未分類へ補完する。
  • Indexはanki_indexを唯一の正本にし、同一variantの再export・再importで同じ値を使う。
  • 001を主シチュエーション内で増える入力番号とするか、1入力内の意味単位番号とするかを合意する。前者ならsituation_sequenceとcounter tableを追加する。
  • 空のAnki profileで「初回import」「同一variant再import」「主シチュエーションと任意レイヤーのdeck階層」「001-01形式の並び」「en-US音声」を確認してからリリースする。

承認後の実装順序: ① 要求定義・設計・APKG仕様・ADR・README/デプロイ手順を改訂 → ② migration作成・検証 → ③ INPUT/LISTS/API/AI/export実装 → ④ typecheck・lint・build・APKG/Anki import検証。承認前にはmigration適用・DB変更・機能実装を行わない。

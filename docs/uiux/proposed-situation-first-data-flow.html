01 / DECISION

この設計で固定すること

CLASSIFICATION ジャンルを廃止する

genre_slug、ジャンル入力、ジャンルfilter、AIのジャンル提案、genre:: Ankiタグをすべて削除する。

PRIMARY + SECONDARY 主と副を1つずつ決める

主シチュエーションは広い場面、副シチュエーションは「久しぶりの連絡」「遊びに誘う」のような目的・文脈。両方をdeck階層に使い、同じカードは複製しない。

STABLE ID IndexはSayDeck固有IDのまま

sentence_variants.anki_indexをAnkiのIndexへ投影する。英語本文の重複に影響されない恒久IDとする。

EXPRESSION LAYERS 01_基本表現のみ必須、02〜04は任意

01_基本表現は必ず1つ作る。02_詳細表現、03_会話表現、04_別の自然な言い方は、実用上の差がある場合だけ生成し、似た文を水増ししない。

設計上の前提: 主シチュエーションの命名はdeck名になるため、AI任せの自由な表記揺れは許容しません。生成前に、そのownerの登録済み主シチュエーション一覧（ID・表示名・安定キー）をAIへ渡します。AIは入力の意図が既存の主に該当するかを判定し、該当すればそのIDを返す。該当しなければ新しい主シチュエーション名を返し、ユーザーの保存確定時にDBへ新規作成します。

副シチュエーションの重複規則: AIは副シチュエーションの基底名だけを返します。保存処理は選択中の主の配下で完全一致を確認し、同じ文字列がすでにあれば末尾に-001を付けます。さらに存在する場合は-002、-003…と3桁連番を増やします。例: 近況を尋ねる と 近況を尋ねる-001 がある場合、次は 近況を尋ねる-002。副の意味的な類似は統合せず、完全一致だけを対象にします。

02 / ANKI PROJECTION

Ankiへ取り込まれるdeckとtags

各variantは、主シチュエーション・副シチュエーション・表現レイヤーから1つだけのdeckへ投影します。Ankiの1 noteを複数deckに複製しません。

SayDeck └── 友人への返信 ← 主シチュエーション └── 久しぶりの連絡 ← 副シチュエーション ├── 01_基本表現 (必須) ← profile_code='basic' ├── 02_詳細表現 (任意) ← profile_code='detail' ├── 03_会話表現 (任意) ← profile_code='conversation' └── 04_別の自然な言い方 (任意) ← profile_code='natural_alternative' 例: SayDeck::友人への返信::久しぶりの連絡::01_基本表現

deck投影の規則: 主と副の組を、1カードにつき1つだけ確定する。副シチュエーションもdeck階層に必ず含め、Anki tagにも同じ分類を投影する。

ノートタイプ

SayDeck。deckのルート名と同名でも、Ankiでは別の名前空間のため衝突しない。過去データを削除する前提で、旧ES1Kv2の8フィールド契約は引き継がない。

Anki tags（同じカードの例）

主: 友人への返信
primary_situation::friend-reply

副: 久しぶりの連絡
secondary_situation::friend-reply::reconnect-after-silence

source::saydecklayer::detail

ジャンルタグは出力しない。主・副シチュエーションの両方をdeckとtagへ投影する。

再分類の扱い: 初回export後に主または副シチュエーションを変更しても、既存Ankiカードを別deckへ自動移動することは保証しません。MVPでは主・副を「登録時に確定する分類」とし、変更は新しい入力として扱います。

主・副分類の利用方針

主は広い場面を表す1件だけ、たとえば「友人への返信」。副はその主の下にある目的・文脈を1件、たとえば「久しぶりの連絡」「遊びに誘う」「近況を尋ねる」として使う。主・副の組が復習用deckを決める。

AI提案とユーザー確定

AIには登録済み主シチュエーション一覧を渡す。既存主に該当すればそのIDを返し、なければ新しい主の基底名を返す。REVIEWの保存時に新規主・副を作成し、対応表のselected_byでAI提案を採用したか、ユーザーが変更したかを残す。

D. generation_profiles — 維持

owner_login、code（basic / detail / conversation / natural_alternative）、語数・文数制約、instruction。難易度ではなく表現レイヤーの定義として使う。basicのみ必須、残りは任意。

E. sentence_cards — 維持

entry_id、position、intent_ja。1つの日本語入力に複数の独立した意味単位がある場合だけ複数行になる。

F. sentence_variants — 維持

sentence_card_id、profile_code、実際に言う英文、和訳、Anki ID、選択状態。意味単位ごとにbasicを必ず1行作り、他の表現レイヤーは学習価値のある差がある場合だけ作る。基本ワードと例文は分けない。

G. audio_assets — 維持

variant_idごとに、Expressionを読む音声を1行だけ持つ。en-USで生成した音声binaryの保存先と検証metadataだけを持つ。

H. anki_exports — 維持

APKG artifactのID、状態、カード数、private storage path、エラーコード。個々のvariantは正本であるsentence_variantsから都度投影する。

I. situation_sequence_counters — 条件付き追加

owner_login、primary_situation_id、last_sequence、updated_atを持つ。001を主シチュエーション内の入力連番とする合意が得られた場合だけ追加し、transactionで重複採番を防ぐ。

J. カード本文・音声のターゲット定義

既存データを削除する前提で、旧来の「基本ワード + 例文」の二重構造を廃止する。各variantが、その場面で実際に使う1つの英語表現を持つ。

04 / END-TO-END FLOW

INPUT → LISTS → EXPORT の全体フロー

1INPUT: 日本語を保存

ユーザーは「言いたいこと」を入力する。任意で最近使った主シチュエーションを選べる。副シチュエーションはAIが必ず提案し、保存前に1つ確定する。ジャンル操作は存在しない。

INSERT expression_entries

（主を先行指定した場合だけ対応表へ仮保存）

2AI: 01_基本表現と必要な任意表現を生成

APIは登録済み主シチュエーション一覧をAIへ渡す。AIは意味単位、必須のbasic、学習価値がある場合だけdetail / conversation / natural_alternative、既存主のIDまたは新規主の基底名、副の基底名を構造化して返す。分類候補はREVIEWの一時状態で保持し、この時点では分類マスタを変更しない。

SELECT active primary situations → AI
INSERT sentence_cards
INSERT sentence_variants × basic（必須）+ 任意の表現レイヤー

3REVIEW: 分類と候補を確定

ユーザーは英文候補、主シチュエーション1つ、副シチュエーション1つを確認する。既存主なら再利用し、新規主ならここで作成する。副の完全一致は保存transactionで-001以降を付ける。01_基本表現を必ず選び、主シチュエーション内の入力番号を採番する案もここで実行する。

UPSERT situation_definitions
UPSERT expression_entry_situations（ユーザー確定）
UPDATE situation_sequence, status='registered', registered_at
UPDATE sentence_variants.is_selected/status

4LISTS: 検索・編集・選択

主シチュエーション、副シチュエーション、表現レイヤー、日付、キーワードで絞り込む。Expressionと和訳は編集できる。登録済みの主分類は変更しない。

SELECT expression_entries + children
UPDATE sentence_variants
UPDATE is_selected

5EXPORT: 音声・APKGを生成

選択variantごとにExpressionのen-US音声を確認・生成し、主シチュエーションと表現レイヤーでdeckを決めてAPKGを作る。

UPSERT audio_assets × 1
INSERT anki_exports
private storageへAPKG保存

6ANKI: import

SayDeckのnoteとして読み込まれる。IndexとGUIDはDBの恒久値を使うため、同一variantの再importでは重複ではなく更新を目指す。

Deck: SayDeck::主シチュエーション::副シチュエーション::表現レイヤー
Tags: source / primary situation / secondary situation / layer

08 / MANUAL VERIFICATION

動作確認: 同じシチュエーション内で複数prefixを持つ入力

主シチュエーションを約束・予定調整に固定し、副シチュエーションを変えながら、短い入力・複数センテンスの入力・会話的な言い換えを順に保存します。これはAIが返す英文そのものを固定するテストではなく、意味単位の分割、主・副分類、連番、任意レイヤー、deck投影を確認するための手動シナリオです。

prefixの設計案: DBには整数のsituation_sequenceを保存し、画面とAnkiのIndexでは3桁ゼロ埋めします。意味単位の番号は既存のsentence_cards.positionから得ます。例: 002-03は「このシチュエーションで2つ目の入力の、3つ目の意味単位」です。999を超えた場合は1000-01と自然に拡張し、文字列切り詰めは行いません。

10 / HUMAN APPROVAL GATE

実装開始前に合意するチェック項目

  • deck名を SayDeck::主シチュエーション::副シチュエーション::01_基本表現〜04_別の自然な言い方 にする。主・副を各1件必須とし、01_基本表現だけ必須、02〜04のdeckは候補がある時だけ作る。
  • ジャンルをUI、API、AI出力、DB、Ankiタグ、LISTS filterから完全に削除する。
  • 主シチュエーションと副シチュエーションを各1件とし、expression_entry_situationsで役割を明示して保存する。副は選んだ主の配下に限定し、主・副の組をAnki deckとtagへ投影する。
  • INPUT生成時に登録済み主シチュエーション一覧をAIへ渡す。AIは既存主に該当すればIDを返し、該当しなければ新しい主の基底名を返す。新規主のDB登録は、ユーザーが保存を確定した時だけ行う。
  • AIは副シチュエーションの基底名を返す。選択中の主の配下に完全一致する副があれば、保存transactionが最小の未使用3桁連番を-001から末尾に付ける。意味的に似ているだけの副は統合しない。
  • ユーザーが分類マスタを直接増やす専用画面はMVPの対象外とし、AI提案を保存することで主・副分類が増える。副シチュエーションは空で保存できない。
  • 既存のジャンル値・表現・音声・APKG履歴は保持せず削除する。新規登録では空の主シチュエーションを許可しない。
  • Ankiノートタイプ名をSayDeckとし、fieldをIndex、Context、Expression、Translation、expression_audioの5つにする。Contextは主・副シチュエーションと表現レイヤーを表・裏の上部に表示するためのexport時生成値とする。
  • Indexはanki_indexを唯一の正本にし、同一variantの再export・再importで同じ値を使う。
  • 001を主シチュエーション内で増える入力番号とするか、1入力内の意味単位番号とするかを合意する。前者ならsituation_sequenceとprimary_situation_idをキーにしたcounter tableを追加する。
  • 空のAnki profileで「初回import」「同一variant再import」「主・副シチュエーションと任意レイヤーのdeck階層」「表・裏のContext表示」「表面だけのen-US音声」「001-01形式の並び」を確認してからリリースする。
